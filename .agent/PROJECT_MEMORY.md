Durable current-state facts useful beyond immediate source inspection.

## Current State

- Swift Package Manager library package/product/primary target name is `SwiftDuckDB`.
- The package uses Swift tools 6.3, Swift language mode 6, iOS 15+ and macOS 12+ manifest deployment targets.
- The tracked repository toolchain pin is `.swift-version` with exact Swift `6.3.3`. `swiftly.pkg` is intentionally absent and must not be recreated unless the maintainer explicitly changes that policy.
- The accepted package baseline integrates exact SwifQL `2.0.0-beta.6.0.1` from `https://github.com/SwifQL/SwifQL.git`; remote SwiftPM validation resolved revision `b759be0f7c64c6ca3b5272d17f404f5084e08033` and passed the complete SwiftDuckDB suite. `Package.swift` is the committed dependency declaration; `Package.resolved` is intentionally ignored local resolution evidence in this repository.
- DuckDB C integration is the internal `Cduckdb` target generated from the official DuckDB `v1.5.5` Swift package flow. The current generated extension set includes `core_functions`, `parquet`, `icu`, and `json`; the generated manifest uses C++11.
- The first public query slice is implemented, validated, independently audited, and documented in the root README.
- Public `Database` is an actor-free `Sendable` final class that owns the database lifetime and can open in-memory or file-backed DuckDB databases.
- `Database.connect()` creates independent public `Connection` actors. Each `Connection` owns one non-Sendable native connection and strongly retains its parent `Database`.
- The only current production `@unchecked Sendable` boundary is internal `NativeDatabase`, the narrow reviewed shared database factory/lifetime owner. `NativeConnection` remains non-Sendable.
- Public async execution accepts `any SwifQLable`. Query preparation uses `.duck` and completes caller-local SwifQL preparation plus exact binding normalization before actor-isolated native execution.
- Each `Connection` serializes its own native execution through a local FIFO gate. Separate Connections do not share one SwiftDuckDB execution gate.
- Async execution uses DuckDB pending execution, cooperative Swift cancellation checks, and same-owner `duckdb_interrupt` when cancellation is observed at the implemented active-pending boundaries. Cancellation surfaces as Swift `CancellationError`; no instantaneous preemption guarantee is made for a synchronous native C call already in progress.
- Public result memory is Swift-owned. `QueryResult` contains legacy `columns`, additive aligned `resultColumns`, rows, and `rowsChanged`; each `ResultColumn` owns a Swift `LogicalType` descriptor with open numeric identity, copied alias/custom identity, Decimal width/scale, and retained recursive metadata. `Row` remains the value owner with positional/named lookup and does not duplicate logical metadata. SQL NULL is explicit `Value.null` while a missing named column returns `nil`.
- Logical metadata recursion/lifetime hardening is validated through deep production zero-row descriptors, post-native-scope retention, duplicate-name alignment, repeated capture stability, unknown raw IDs, and multi-level direct-C child-handle/string ownership tests. The fresh independent logical-metadata root audit is accepted CLEAN with zero blockers.
- The pre-B native probes are accepted. P01 freezes exact DATE/TIME/TIME_NS/TIMESTAMP S/MS/us/NS finite ranges, infinity sentinels, precision/divisibility, 24:00, checked-overflow, and negative-floor rules. P02 freezes exact TIMESTAMPTZ signed-microsecond ↔ Foundation.Date conversion through a bidirectional per-value equality predicate; the largest contiguous guaranteed subset is `[-7_611_627_392_000_000, 9_568_241_792_000_000]` microseconds, but sparse exact values outside it remain valid when the predicate succeeds.
- The non-Decimal exact driver vertical has B1 Int128/UInt128/UUID accepted, B2 PureDate/PureTime/DateTime accepted, B3 Foundation.Date/TIMESTAMPTZ accepted, and B4 Interval accepted after Root Audit 01 B01/B02/B03 Correction 01 plus fresh Root Re-audit 01 CLEAN. B5 is regression/concurrency/external-consumer hardening and is next/separately gated; R3 follows B5. Decimal remains P03/Wave-C gated, and nested/complex `Value` materialization remains unimplemented.
- Current public `Value` is a struct facade with hidden exhaustive storage. Supported scalar families are null, Bool, signed/unsigned 8/16/32/64-bit integers, Float, Double, String, Foundation Data BLOB, UUID, exact Int128/UInt128 through macOS 15+/iOS 18+ availability-gated bridges, PureDate, PureTime, DateTime, Foundation.Date as exact TIMESTAMPTZ, and shared `SwifQL.Interval` as exact DuckDB `INTERVAL`. Hidden 128-bit word storage keeps the package buildable at macOS 12/iOS 15; no timezone identifier/offset metadata is preserved.
- B2 assigns stable `Value.Kind` identities 17 = date, 18 = time, and 19 = dateTime while Kind 0...16 remain unchanged. B3 assigns `Value.Kind.timestampTZ == 20`; `Value.timestampTZ`, `get(Date.self)`, `timestampTZValue`, and Row Date conveniences preserve the exact family. `NativeTemporalCodec` owns B2 mapping, while `NativeFoundationDateCodec` owns the P02 exact signed-Int64-microsecond/Foundation.Date conversion. The B01 finite `PureDate` civil-domain guard precedes `duckdb_to_date`; standalone exact `PureTime` `24:00` is supported; DateTime precision is exact with no rounding and negative timestamp decomposition is floor-consistent.
- Prepared Date binding accepts only targetless or resolved `TIMESTAMPTZ`, with P02 exact per-value equality and no tolerance/silent rounding. Appender Date conversion and typed-value creation occur in whole-row Phase 1 before native mutation; deterministic Date failure mutates zero native columns and is recoverable, while native Phase 2 failure remains terminal. NativeResult reads `duckdb_timestamp.micros` and rejects infinity, non-finite, or otherwise non-exact Date values through `invalidResult`; `ResultColumn` preserves TIMESTAMPTZ identity.
- B4 uses shared `SwifQL.Interval` as the public semantic type with no duplicate SwiftDuckDB Interval type. `Value.Kind.interval == 21` and IDs `0...20` remain unchanged; `Value.interval`, `get(Interval.self)`, `intervalValue`, and Row Interval conveniences are accepted. `NativeIntervalCodec` owns exact finite conversion: months/days use `Int32(exactly:)`, microseconds stay `Int64`, and mixed-sign/non-normalized components are preserved. Infinities and out-of-native-range months/days survive generic normalization and reject at native Prepared/Appender boundaries. Prepared binding calls direct `duckdb_bind_interval`; Appender conversion is whole-row Phase 1 and recoverable on deterministic failure, followed by direct `duckdb_append_interval` Phase 2, whose native failure remains terminal. NativeResult uses validity-first direct `duckdb_interval` vector access, preserves the legitimate all-minimum triple, and never infers validity from `duckdb_get_interval` sentinels. Ordinary SwifQL uses plain Interval/Optional transport while `Value.interval` uses dynamic routes. The transaction `.binding` first-reason identity remains protected.
- Public `DatabaseError` distinguishes database/connection opening, preparation, binding, execution, unsupported binding/result type, invalid-result failures, reusable-Statement template/argument/ownership/usability failures, transaction lifecycle/scope failures, Appender scope/row/finalization/cleanup failures, and terminal `.connectionUnusable` state.
- Query-centered `SwifQLable.query(on:)` / `.execute(on:)` are thin delegates to the same Connection engine.
- Public reusable `Statement` is a `Sendable` final class created by `Connection.prepare`; it strongly retains its originating `Connection`, stores no native handle, and identifies its actor-owned native prepared statement through an internal registry id.
- `Connection.prepare` supports a fixed-only direct SwifQL query and a builder form whose private `Statement.Parameter` values define dynamic arguments. Fixed and dynamic native slot order comes from one SwifQL Duck preparation with same-render unsafe-value provenance.
- Every reusable execution clears prior native bindings and fully rebinds the immutable fixed/dynamic layout before using the existing pending execution engine. There is no automatic reprepare or public native parameter-index API.
- Ordinary `Statement.query` / `execute` use the existing Connection ordinary FIFO scheduler. Explicit `Statement.query(on:)` / `execute(on:)` use the existing owning-Transaction operation FIFO without acquiring the outer ordinary lease.
- Statement/Transaction owner mismatch is rejected before operation registration. Matching-owner transaction execution registers before argument-count/type normalization so caller-local failures participate in rollback-only first-reason semantics and cannot false-commit when caught.
- All four public Statement async operations retain the Statement through completion; deinit only schedules idempotent registry removal on the originating Connection actor, preventing the Statement's own cleanup from racing its queued/native-active operation.
- A fail-closed Connection dominates Statement execution with `.connectionUnusable`; clear-bindings failure is separately contained as a terminal Statement-local tombstone and does not auto-reprepare or fail-close the whole Connection.
- Public scoped `Appender` is a `Sendable` final class supplied only by `Connection.appender(to:)` for `Path.Table`, `Path.SchemaWithTable`, and `Path.CatalogWithSchemaAndTable`; it stores no native handle and exposes only complete-row `append(...)`.
- A live Appender scope holds one ordinary Connection admission for the complete awaited body. Native Appender state is owned by the Connection actor registry, and `NativeAppender` strongly retains `NativeConnection` while DuckDB's Appender holds only a weak client context.
- Appender row calls perform cancellation/count/full normalization before actor entry, recheck cancellation on the actor immediately before synchronous native mutation, and serialize each complete row as one actor-owned native operation. Concurrent public row calls therefore cannot interleave columns.
- Wrong Appender row width and unsupported Swift values are caller-local/recoverable before native mutation. The first native primitive/end-row failure is terminal, is synchronously consumed/discarded, is stored as authoritative first-terminal truth, and cannot be converted to a successful scope by catching it inside the body.
- Body error/cancellation paths explicitly discard still-buffered Appender data before ordinary-admission release. Ambiguous native clear failure conservatively fail-closes the Connection before release; later work receives `.connectionUnusable`.
- Inherited same-Connection ordinary Connection/Statement work, transaction start, and nested Appender are rejected while the Appender body is live; separate Connections remain independent. Deliberately TaskLocal-erased external same-Connection work is treated as external and may form a caller dependency cycle if awaited from the exclusive body.
- Normal escaped Appender use after scope finalization returns `.appenderEnded`, while fail-closed Connection state may dominate.
- Ordinary Appender scope is explicitly non-atomic. Pinned DuckDB may auto-flush earlier rows before the Swift body ends, so later body error/cancellation cannot promise rollback of already flushed data. Appender-in-Transaction is not part of the first slice.
- Current Appender row values are `Value`, recursive Optional/NULL, Bool, signed/unsigned 8/16/32/64-bit integers plus Int/UInt, Float, Double, String, Foundation Data, UUID, availability-gated Int128/UInt128, PureDate, PureTime, DateTime, Foundation.Date, and `SwifQL.Interval`; Foundation.Date maps only to TIMESTAMPTZ under accepted B3/P02 exactness semantics, while finite Interval maps only to DuckDB INTERVAL with exact Int32 month/day narrowing and Int64 microseconds. Mixed signs/non-normalized components are preserved; semantic infinity and out-of-Int32 month/day values reject before native row mutation. Temporal/Interval conversion and typed-value construction occur for the whole row in Phase 1 before native mutation, so deterministic failure is recoverable and mutates zero columns; native Appender Phase 2 failure remains terminal. Decimal/nested/complex expansion remains gated.

- Typed-table selected-column syntax such as `User.select(\.$email, \.$name, \.$role)` is implemented as SwifQL `TableSelector` construction sugar and preserves ordinary SwifQL `where`, `orderBy`, `limit`, alias, and related composition.
- Public `Connection.transaction` is implemented as a caller-isolated async scoped capability. The supplied `Transaction` is `Sendable` and represents exact same-Connection transaction authority without owning native handles.
- Each `Connection` permits at most one pending or active transaction reservation. Separate Connections retain independent transaction/admission/fail-close state.
- Transaction query/execute registers operation state on the Connection actor before caller-local SwifQL preparation; reservation-local native execution is FIFO with at most one native-active operation.
- A transaction operation failure makes the scope rollback-only even when the body catches that error; the first rollback-only reason is retained, non-active siblings are terminally resolved, and a later successful body return cannot false-commit.
- Finalization closes new transaction work, invalidates escaped/non-active capability use with `.transactionEnded`, and waits only for already-native-active work to drain.
- Successful body completion commits only after COMMIT succeeds. Body error/cancellation rolls back; mandatory rollback cleanup failure fail-closes the Connection.
- User BEGIN/COMMIT/ROLLBACK is rejected through the normal Connection and Transaction query/execute routes using prepared-statement transaction classification.
- COMMIT setup failure before native scheduling performs mandatory rollback cleanup and can leave the Connection reusable when cleanup succeeds. Any surfaced COMMIT error after native scheduling has been attempted receives no compensating rollback/retry and terminally fail-closes that Connection because a safe native transaction postcondition is not publicly machine-readable.

## Reviewed Direction

- The library baseline is Swift 6.3+.
- Intended platforms are iOS 15+, macOS 12+, Linux, Android, and Windows; each support claim requires actual platform/toolchain evidence.
- DuckDB integration stays behind a thin public-C-API boundary unless separately reviewed evidence justifies another boundary.
- High-level database APIs use Swift structured concurrency, `async`/`await`, and truthful actor/Sendable ownership while preserving independent concurrency where DuckDB semantics permit it.
- SwifQL remains the mandatory query-construction layer. SwiftDuckDB must not grow a competing SQL DSL or ordinary String execution API.
- README executable usage uses SwifQL only; plain SQL may appear only as explanatory comparison, and raw SQL is documented only as an explicit escape hatch.
- The desired database UX is concise and Swift-native while keeping concrete database/connection ownership visible.
- Development proceeds capability by capability. Scoped transactions, the first reusable prepared-statement slice, the first scoped Appender slice, B1 Int128/UInt128/UUID, B2 PureDate/PureTime/DateTime, B3 Foundation.Date/TIMESTAMPTZ, and B4 Interval are implemented current state. B5 hardening is next and separately gated; R3 follows B5. Decimal, nested/complex values, Appender-in-Transaction/advanced Appender surfaces, Codable/model decoding, pooling, observation/reactivity, migrations, and additional platform validation remain separately gated future work.
- The maintainer explicitly wants reusable-prepared-statements and Appender explanations/examples preserved for future articles/publications. `.agent/FUTURE_PUBLICATIONS.md` records implemented API/source-material truth; publication backlog entries still do not authorize another capability or imply a release/publication event.
- Repository work is role-specific and interface-agnostic: coordinator/reviewer and independent-auditor sessions use their configured approved repository interfaces, while a direct local implementation/validation executor uses its own local repository/filesystem/Git/shell tools for executable fallback work. A local executor must not depend on a coordinator/auditor-only repository bridge, and transient handoffs/prompts own any concrete tool names for the current environment.
